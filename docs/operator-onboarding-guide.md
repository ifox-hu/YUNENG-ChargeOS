# 配置化运营商接入

本功能复用原有多租户账号、角色、菜单和设备模型，不复制一套运营商代码。本地验证使用模拟设备；未接入真实厂商协议或真实短信服务。

## 使用顺序

1. 迁移前备份数据库。在项目根目录执行 `node scripts/migrate-operator-onboarding.cjs`。脚本先检查管理员账号重名，再添加唯一约束及规则表；发现重名会停止，不自动删除或合并旧账号。
2. 平台管理员（用户 ID 为 1）在“系统管理 → 租户管理 → 运营商开户”设置编码、名称、管理员账号、8～20 位初始密码、有效套餐及到期日。套餐不能包含平台租户管理权限。
3. 通过安全渠道交付初始凭据。开户成功会在同一事务中初始化部门、岗位、管理员角色、账号、关系及默认充电规则；本地流程不发送邮件或短信。
4. 运营商使用自己的账号配置站点、模拟桩及端口。在“运营管理 → 充电规则”设置最长充电时长、白名单开关及本运营商会员。
5. 本地测试注册页填写运营商编码，会员与余额账户绑定同一运营商。A 的规则不影响 B；启用空白名单时禁止所有会员新启充。

## 边界与一致性

- 后台身份和租户取自服务端登录态，不能通过请求头切换运营商。
- 设备父子资源与会员归属不可跨租户迁移。后台详情与内部服务入口分开授权。
- 规则修改、白名单修改均递增版本；过期表单返回冲突，刷新后重试。
- 启充事务共享锁定规则，配置修改排他锁定同一规则，避免读取混合版本，也避免把同一租户的所有端口串行化。
- 停用或到期禁止新注册、登录和启充；既有有效登录态仍可安全停止、结算及补偿。真实微信分支补充了生命周期检查，但本地未配置微信凭据，不作为真实微信联调通过的证据。
- 演示租户兼容由 `hcp.demo-tenant.enabled` 显式开启，默认关闭。本地 Docker override 开启；已有 9999 记录仍须有效。
- 模拟器按数据库记录的设备归属执行持久化操作，不把设备默认归入 9999。

## 验证与量化口径

`scripts/test-operator-onboarding.cjs` 经过真实网关、登录态、业务 API、MySQL、RocketMQ 与模拟器验证两家运营商。每次使用随机专用租户，结束后清理本次数据和登录态。结果写入 `docs/test-results/operator-onboarding-2026-11-07.json`。

开户接口耗时仅代表本地 API 调用耗时，不等于人工接入周期。双运营商业务验证不是压测，不写成生产运营商规模或真实硬件吞吐能力。历史充电、积分和告警压测数据不自动计作本次重测。

## 回退

先停用新开户及配置入口，再还原应用。保留新增表、已开户账号及其业务数据，不通过删除租户、订单或会员回退。已启用的白名单需要明确处理，不能卸载校验后静默放开启充。删除 system Dockerfile 中的应用目录匿名卷声明，是为了避免新镜像继续运行旧 JAR；旧匿名卷不自动删除。
