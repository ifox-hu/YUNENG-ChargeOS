# 本地充电运营业务完善方案

日期：2026-11-14

## 目标与已确认范围

用户选择：在现有项目上实现完整本地业务，参考慧知商业演示优化仪表盘、异常订单、模拟退款、对账、分账及基础营销；不做真实设备接入。

成果应可通过运营后台操作，并在本地数据库看到一致的业务记录。GitHub Pages 同步提供浏览器模拟体验，明确区分演示数据和真实后端数据。

## 实现方式比较

1. 只改页面：交付快，但财务操作没有服务端记录，不能满足本次完整本地业务要求。
2. 现有项目内补齐本地业务（用户已选择）：复用账号、租户、订单、余额、权限和前端组件，新增必要流水和业务页面。工作量适中，可以逐阶段验证。
3. 接入真实支付等外部服务：需要商户资质、凭据和外部联调，不在本轮选择范围内。

## 当前代码基础与约束

- 首页与经营管理页大段重复，已有经营汇总、站点/桩统计和导出接口，但缺少仪表盘趋势与业务下钻。
- 订单状态已有下单、取消、支付成功、退款、完成、结算中、手动结算；不能直接增加相同含义的另一套订单状态。
- 余额已有本地模拟充值及唯一请求号流水；当前模拟充电结算不等于实际余额扣款。
- 积分已有 Outbox、幂等入账、重试补偿；工单已有闭环与租户权限校验。
- 当前源代码已移除 Java 测试类。本轮不重新引入 Java 测试目录，使用独立接口回归脚本、构建和实际页面验收。
- 延续原有 Controller / Service / Mapper 结构、四空格缩进和中文业务说明；复用 Vue 2、Element UI、ECharts 和既有依赖，不换技术栈。

## 第一阶段：仪表盘与经营统计

- 首页改为仪表盘，保留独立经营报表页，减少重复代码。
- 显示订单结算金额、模拟实收净额、电量、订单数、设备在线状态和待处理事项，明确区分结算金额与已收款金额。
- 支持近 7 天、近 30 天和自定义日期；所有日期条件统一按北京时间、包含起始日和截止日处理。
- 支持站点筛选，展示订单/电量/金额趋势、设备状态分布、站点排行。
- 待处理卡片可跳转异常订单、故障工单、失败积分事件，并携带筛选条件。
- 没有数据时显示真实空态；接口失败显示错误与重试，不用随机值或补零掩盖失败。
- 经营报表保持现有搜索、分页和导出，统一指标口径及金额、电量、时长单位。

## 第二阶段：异常订单处理

- 集中查询启动结果待确认、超时未结束、结束/结算信息不完整、费用合计不一致等可由数据库判断的异常。
- 异常类型与业务处理状态分离：订单仍沿用原状态，处理记录单独留痕。
- 支持订单详情、结算日志、处理人、处理说明和处理时间。
- 普通备注不改变订单；重新核查仍有异常时不可仅靠“已处理”隐藏问题。
- 允许在已确认未启动、无电量、无收费记录的待启动订单上执行安全取消；禁止从页面强制把正在充电或结果不确定的订单改成完成。
- 重复动作保持幂等；写入前锁定并复核订单状态及租户归属。

## 第三阶段：本地支付与退款

以下业务规则为本方案的实施默认值，待本方案整体确认后采用。

- 采用本地余额模拟支付，不调用微信、银行或其他真实资金渠道；仅本地配置显式开启时可操作。
- 为已结束且费用有效的本地模拟订单提供付款入口，校验会员、租户、订单状态，锁定订单与账户后完成余额扣款及支付流水。
- 每张订单最多形成一笔有效付款；重试不重复扣款。扣款不足时整笔失败，不允许负余额。
- 完成订单付款后仍保持原充电终态，不改成“充电中”或把完成状态退回支付状态；支付记录单独表达资金状态。
- 历史订单只有结算金额、没有成功扣款流水的，标记“未纳入本地收款”，不能直接退款增加余额。
- 已成功模拟付款的订单支持填写原因并提交部分/全额退款；金额精确到分，大于零且累计退款不超过实付。
- 退款成功在同一事务中更新退款记录、账户余额、余额流水及累计退款金额；重复请求只返回原结果。
- 部分退款保持订单完成状态；全额退款才进入原有退款终态。通过付款、退款记录展示资金状态，不复用充电状态表达资金状态。
- 原有积分规则不暗中改成退款扣积分；本轮明确标识“充电完成奖励”，退款不自动追扣，避免与已消费积分及现有异步发奖产生隐性耦合。
- 收口旧充值入口，不能绕过登录态、本地开关和受控金额直接修改任意用户余额。

## 第四阶段：对账与本地分账

- 对账范围明确为本地订单、支付/退款流水、余额流水及分账记录，不宣称完成支付渠道对账。
- 按业务日期发起对账；核对逐笔支付扣款、退款入账、累计退款及分账合计，展示匹配、差异和未纳入记录。
- 保存对账批次、统计、逐笔差异和处理备注；重新执行生成新批次，不覆盖历史证据。
- 分账基础为模拟实收减已退金额，不将优惠前金额或纯结算订单纳入分账。
- 先支持平台与站点两方，按运营商配置分成比例，两方合计 100%，金额精确到分，舍入尾差固定归站点方。
- 分账记录保存规则快照；后改比例不影响历史分账。重复执行不重复记账。
- 分账后的退款采用冲正记录调整各方应得，保留原分账记录，不能直接改写历史金额。
- 每次冲正按原比例快照计算“累计退款后的净收应分金额”，与已有净分账额求差，避免多次部分退款逐笔舍入导致累计金额不平；未分账前退款只减少待分账基数。
- 本地分账只形成可核对台账，不进行银行卡出款、提现或真实商户分账。

## 第五阶段：基础营销

- 首版支持满减券模板：名称、门槛、优惠金额、有效期、发行数量、启停状态。
- 后台向本运营商会员发券，记录批次和领取记录；停用模板禁止继续发放，不直接删除已发券。
- 每笔本地付款最多使用一张券；校验会员、租户、有效期、门槛和未使用状态，再与付款同事务核销。
- 优惠金额不超过订单费用；页面分别显示结算金额、优惠、实付、已退和净收。
- 全额退款后券恢复为未使用；已过期的券依然不能使用。部分退款不退券。
- 优惠为零实付订单不增加余额、不产生正额分账；以核销记录保持一次性使用。
- 零实付订单需要撤销时走撤销核销流程，禁止制造正额退款流水；恢复优惠券仍须遵循原有效期。
- 优惠券入口同时覆盖后台本地付款操作和小程序本地订单付款页；不添加未接通的营销按钮。
- 本轮不扩展 PLUS 会员、团充、IC 卡、车辆、发票或多级代理分润；这些是后续独立业务，不以空菜单代替实现。

## 权限、数据与兼容

- 租户和操作人取自服务端登录态，不接受客户端自报租户覆盖服务端身份。
- 各新增查询和写入都校验权限与资源归属；平台管理员跨租户查看需要显式选择目标，普通运营商不能越权。
- SQL 迁移为增量、可重复执行，不删除已有订单、余额和工单，不批量修改历史费用。
- 本地验证数据使用唯一前缀，并单独清理；不将编造收入或回填历史付款当作真实业务。
- 表和索引围绕已确认的付款、退款、分账、对账和优惠券生命周期建立，不引入通用工作流引擎或新微服务。
- Pages 模拟接口与真实接口保持一致的字段和金额规则；Pages 操作只保存在浏览器，并持续显示演示标识。

## 验收与交付顺序

按仪表盘 → 异常订单 → 本地付款退款 → 对账分账 → 基础营销依次交付；每一阶段都能在现有应用内运行。

最低验收：

1. 两家运营商的数据、查询和写入隔离；非法访问不能修改数据。
2. 仪表盘和报表按同一日期/站点条件能与数据库汇总对齐，空态与失败态正常。
3. 异常订单可核查、可留痕；不允许通过重复操作或人工处理破坏终态与结算数据。
4. 同订单并发付款最多扣一次；余额不足无副作用；重复/并发退款不超退。
5. 无实付历史订单不能退款到账；折扣、退款、实收和分账合计逐笔一致。
6. 已分账订单退款有冲正记录；调整分成比例不改写历史记录。
7. 同一张券并发核销最多成功一次，跨会员、跨租户、过期及未达门槛券均被拒绝。
8. 独立脚本验证正常链路与关键失败回滚；后端编译、前端构建和实际页面交互通过。
9. 文档列出本地模拟范围、迁移和启动方法；只报告本轮实际执行的验证，不编造性能指标。

本方案确认后再进入实现和逐阶段验证，不自动推送 GitHub。
