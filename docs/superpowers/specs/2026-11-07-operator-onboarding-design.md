# 运营商配置化接入设计

日期：2026-11-07。状态：设计草案，待用户确认后编写实施计划；不是已实现功能或测试结果。

## 1. 目的与已确认范围

用户已选择先做“运营商配置化接入”，而非多厂商协议接入。在已有慧知多租户底座上补齐运营商开户、账号交付、设备配置、可选充电规则及双租户端到端隔离验证。新增运营商通过数据配置接入，不为每个运营商增加策略类。

保留个人开源二开性质，明确已有能力与本次贡献。不预设接入效率、成功率、吞吐提升或生产规模。量化来自实际测试与留存的对账结果。

## 2. 现状与约束

- `SysTenantServiceImpl.insertSysTenant` 已在事务内创建租户、部门、岗位、管理员、角色及套餐菜单。不能将这整套底座能力当作本次从零开发。
- `createUser` 随机生成初始密码，并在数据库事务中调用短信/邮件；本地未配置外部通知时影响开户与账号交付。
- `SysTenantController` 有权限注解，但平台开户能力还需显式核实调用者是否为平台超级管理员，不单独依赖可被分配的菜单权限。
- `AuthFilter` 现只重写用户/部门身份，`HeaderInterceptor` 先从 header 读取租户，即使取到 LoginUser 也未覆盖该租户上下文。本期须将后台可信租户上下文修正为来自已验证 token 对应 LoginUser 的 SysUser.tenantId，验证伪造 header 无法切换租户；不能只在新页面隐藏租户输入。
- `AccountLoginService.register` 当前将会员和余额账户归属固定为 9999，手机号验证码仅为本地测试，不证明手机号真实归属。
- 现有充电会员校验要求会员与设备同租户；本期保留“一份会员账户归属一个运营商”的模型，不改为跨运营商统一钱包。
- 充电校验链已有 4 类强制校验；设备策略仅落地模拟器。订单预占使用短事务和端口行锁；远程设备调用在事务外。
- 告警和工单已有设备租户校验与活动工单唯一约束。本期复用，发现所选链路的隔离问题时修复，不扩大为所有历史模块的安全审计。
- 工作区含用户私有简历材料和未跟踪输出，必须保留，不整库暂存、不上传。
- 不增加中间件，不升级 Java/Spring/Vue，不重写已有交易、积分及告警机制。

## 3. 方案与取舍

方案 A（用户已选择）：复用租户底座，补充有明确权限的运营商开户入口、规则配置和双租户验收。最小改造，直接验证运营商接入。

方案 B（本期不做）：在 A 上增加第二种模拟设备协议/策略。能验证设备厂商扩展，但不等于租户开户，另行开展。

不采用每家运营商一个 Java 策略类，也不建设通用规则脚本引擎或 Java SPI 热加载框架。

## 4. 身份和安全边界

- 平台管理员沿用现有 userId=1 的超级管理员判定；租户编码 9999 本身不构成管理员授权。
- 运营商管理员是该租户下的后台账户，通过身份、资源归属和套餐内角色权限操作。
- 终端会员账户经登录取得 token，资源访问的会员身份和租户从服务端账户/设备派生，不信任请求体/header 的 tenantId 或 memberId。
- 新开户、任意租户规则管理只允许平台管理员；运营商管理员仅能管理本租户允许的规则、白名单及设备。无凭证/普通会员不能调用后台配置接口。
- 客户端提交的租户编码仅用于明确选择注册归属，不作为授权凭据；注册目标必须存在、正常、未删除、未过期。
- 禁用/到期租户不能新注册、新登录或新启充；不简单切断停止充电、已发生交易的结算回调、积分/告警补偿，避免制造悬挂订单。已有 token 必须在新增/受影响的业务入口再次检查状态。
- 平台管理员可按授权查看各租户，但越权测试使用真正的非 root 租户账号，不能靠换 header 冒充登录。
- 网关/服务拦截器以已验证后台会话重写用户、部门、租户上下文；内网 Feign 调用必须保留原有身份透传/内部来源验证。公开无 token 路径不能凭 header 建立受权后台身份；会员 token 与后台 JWT 不混用。认证基础改动需回归 system/operator/mp 内部调用，不扩大为公开暴露微服务端口的网络安全项目。
- 具体信任路径（实施者提案）：网关从已验证 token 对应服务端会话取得身份并覆盖身份头；公共 HeaderInterceptor 在取得有效 LoginUser 时再次以其 SysUser 覆盖上下文，不能保留外部 tenant header。平台跨租户业务使用独立 targetTenantId 参数，仅可信 userId=1 可指定，先验证目标租户，再在授权服务范围执行 TenantUtils.execute，结束恢复原上下文；此参数不改变登录身份或授予权限。非 root 的 tenantId/targetTenantId 与真实租户不一致则拒绝，不自动跟随客户端。
- 停用/到期的运营商后台不提供新的受限维护登录；一期由平台管理员兜底处理在途业务。终端会员的有效既有凭证只可继续本人订单的安全停止/查询等明确允许路径，不能新启充；后台补偿按持久化事实运行。停止与结算入口仍须认证或可信内部来源，不能为了恢复放开匿名写入。
- 演示9999可能没有sys_tenant行，不自动捏造该行、套餐或永久有效期。保留显式本地开关 `hcp.demo-tenant.enabled`（默认false，仅本地Compose开启），只对既有9999演示身份在租户不存在时兼容；存在实际行时仍尊重停用/到期。该例外不授予root权限、不适用于其他编码；关闭开关时缺失租户一律拒绝。与既有localTest注册开关分别说明，两者均开启才允许缺省9999演示注册。实际测试A/B必须有真实租户行且不能走该例外。

## 5. 开户及账号交付

在现有租户管理内增加独立的“运营商开户”操作和对应后端入口，底层提取/复用租户基础数据初始化逻辑，避免复制两套部门、角色和账号创建代码。

输入：租户编码、运营商名称、管理员用户名、初始密码、联系方式、有效套餐、到期日。初始密码由平台管理员在受保护表单中指定，掩码输入，按现有 BCrypt 存储；不返回密码、不写入操作日志/SQL日志/测试报告/截图。现有账号规则保持兼容。

此入口不依赖短信/邮件，也不声称交付了通知能力；页面明确提示管理员通过独立安全渠道交付账号并提醒修改密码。不新增模拟短信来冒充通知成功，不自动对外发送消息。

开户一个本地事务提交租户、默认部门/岗位、管理员角色、套餐菜单、管理员账号及关系、默认规则。套餐必须存在、可用且菜单编号有效。任一步失败全部回滚。必须在提交前验证角色菜单不能授予平台专属租户管理/开户权限，不能让恶意套餐赋予 root 能力。

租户编码和管理员用户名不能重复，数据库约束和事务失败处理兜底并发，不能只用先查后写。重复提交返回明确冲突，不新建第二套数据；本期不承诺重复响应中重放敏感密码，也不做通用幂等平台。既有数据若存在冲突，迁移应报告并阻止加约束，不能删除或合并用户数据。

原租户新增接口需防止成为绕过上述平台授权与基础验证的路径；可保留旧通知模式，但通知不得放在持锁事务中，失败不回滚已交付的账号，并返回明确通知状态。新开户仍使用显式初始密码方式。

## 6. 配置化充电规则

本期仅提供两个真实可验证的可选业务规则（实施者提案，不是用户已提供的现有事实）：

1. `maxChargingHours`：运营商允许的最大充电时长，取值 1..24，默认 24；不能突破既有参数安全边界。
2. `whitelistEnabled`：是否仅允许该运营商白名单会员启动充电，默认 false；启用后空名单拒绝所有新启动，不能失败时放行。

新增增量表建议：运营商规则表，tenant_id 主键、上述字段、version、更新时间及修改者；运营商白名单表，(tenant_id, member_id) 唯一，记录加入者和时间。白名单成员必须归属本租户，不接受任意外租户会员 ID。

数据所有权：规则由 operator 业务模块维护，新开户以同一数据库事务写入安全默认值；避免在创建数据库事务中跨服务 HTTP 初始化。system 与 operator 当前共享业务数据库，可将小型默认初始化服务/SQL放在明确边界，不把设备业务塞进租户角色管理。具体 mapper/共享 DTO 的放置由实施者决定，禁止循环模块依赖。

规则读取以已校验的设备/端口租户为准，在新订单生成前执行。现有参数、用户租户、设备端口、活动订单四类强制校验始终运行；可选规则不能跳过它们。配置读取不增加远程 RPC，不放大端口持锁事务。

规则更新用版本号条件更新；旧版本写入返回冲突，不静默覆盖。规则与白名单读写需保证单次启动决策一致：现有预占事务在端口锁之后，以共享读锁读取租户规则；规则/名单修改先排他锁定同一规则行，再修改名单，不持有或反向申请端口锁。不同端口的启充允许共享读取同租户规则，避免被一把排他锁串行化。名单变更也递增版本，使表单冲突可见。使用数据库当前锁定读获取名单，避免旧快照混合新规则；具体SQL以实际MySQL版本文档及真实并发测试确认。

迁移为所有已有正式租户及演示9999补充默认规则行，新开户同事务初始化。不得在每次启充时UPDATE/INSERT默认规则制造排他竞争。迁移前部署旧版本，迁移后再开新入口；迁移完成后若规则意外缺失，明确返回配置未就绪，不因数据库异常默认放行。既有租户通过默认初始化保持业务兼容，不依赖运行时无记录fallback。

规则只约束新启动，不追溯取消既有充电订单。新增规则节点允许一次性改造启动上下文，但后续相同数据依赖的规则扩展不改主流程。不是运行时上传 Java 代码或随意关闭节点。

## 7. 终端会员归属

在现有本地测试注册开关下，注册请求/页面支持选择明确的租户编码，服务端验证租户有效性后，将会员与余额账户归属写入同一租户，保持事务一致。

兼容原演示：未传租户编码时，仅在既有 localTest 开启且9999符合第4节演示开关/生命周期规则时沿用9999；其他情形拒绝缺失归属，不把客户端header直接透传为租户。现有demo账号在明确本地配置下仍可登录。

账号名和手机号暂沿用全局唯一，不迁移成复合唯一、不改变现有登录输入。登录从持久化账户查询会员租户并验证，不靠用户选项覆盖会员归属。不会接入真实短信或微信授权，不声称公开生产注册已完成。

## 8. 设备配置与两家运营商流程

复用现有站点、充电桩、端口管理页面/API。列表/详情/新增/修改必须由服务端绑定本租户，并校验站点→桩→端口的租户关系。外租户 ID、伪造 tenantId 请求不得读取或转移资源。平台管理员指定目标租户需走明确受权路径，不能用随意客户端切换规避绑定。

不在开户时自动生成测试站点和测试设备。开户完成后按正常业务页面/API配置模拟设备；测试脚本也优先调用这些接口，不能只 INSERT 数据就宣称设备配置链路通过。

工单沿用原功能；设备告警事件仍按实际设备租户派生和校验，不改变老事件/租户转移保护。运营商管理员的处理与会员确认分开验证。两家运营商使用同一现有模拟设备策略，而不是复制厂商代码。

## 9. 界面与发布边界

沿用 Vue 2/Element UI 家族样式；在现有租户管理增加开户能力，在运营商配置区域提供规则与白名单管理，不新建独立管理前端。终端注册页面增加必要归属字段，不改整站视觉。

本期验收本地真实后端；浏览器展示、API和数据库持久化必须一致。GitHub Pages 是独立浏览器模拟，不计作真实隔离证据。本期不自动发布 GitHub/Pages，不改面试软件，不编辑简历。

## 10. 验证与量化

先编写失败测试再实现。证据分单元、真实数据库、经网关的身份/API、浏览器、完整模拟充电，不将某一层通过当作全部通过。

必测清单：

- A、B 两租户经开户入口创建，初始化数据逐项对账；两个真实管理员能登录，套餐菜单匹配，凭据不出现在日志/报告。
- 无权限开户、无效/停用套餐、非法租户编码、管理员重复、租户重复、并发重复开户被正确拒绝；末端故障注入无半套租户/角色/账号/默认配置。
- A/B 均经业务接口配置站点、模拟桩和端口；伪造归属/交叉父子资源不改变数据。
- A 配置白名单且限制时长，B 保持默认；A 白名单内允许、名单外/外租户会员拒绝，A超时长拒绝，B不受A规则影响；非法启动无订单、日志或积分事件副作用。
- 跨租户规则读取、修改、加白名单、设备/订单/工单/告警列表与详情、工单操作与告警重放被拒绝，且数据库不变。两方对称测试，不能仅测A→B。
- 规则版本冲突、白名单与规则并发修改、重放重复开户不产生重复初始化数据。
- 两家分别跑通完整模拟充电、结算与关联积分事件；告警接入到处理、报修到工单解决/会员确认，验证本租户可见、外租户不可见。
- 停用/到期不能新开户成员/登录/启充；此前正在充电订单仍可安全停止并完成应有回调。
- 旧9999演示、原4类/12项校验、积分可靠投递、告警幂等、停止结算和工单状态回归；不覆盖已有运行数据。
- 后端构建、定向前端检查/构建、实际浏览器操作均需验证；保存执行版本、环境和结果。

量化只统计实跑结果：开户成功/拒绝/回滚用例数、创建后的数据库关系条数、受权/越权用例数、配置生效断言、双租户完整业务成功数及实际开户API耗时。开户API耗时不当作人工接入周期；没有受控旧版基线，不写“接入缩短几天/提升60%”。不以大量空租户创建数量替代正确性。

测试夹具使用唯一前缀和专用租户编码；只清理本次创建的租户、角色、会员、设备、订单、事件与登录态，顺序按关联依赖执行，并输出清理对账。原始输出留本地、可公开报告脱敏，不写密码/token/个人联系方式。

## 11. 迁移与回退

新增表和必要约束采用可复跑增量SQL，迁移前检查旧数据，不改写现有租户和订单归属。迁移预先填充安全默认规则，包括9999演示规则，新接口上线须先迁移数据库；规则缺失明确拒绝启动，不静默放行。

回退时停用新开户/配置入口并还原应用代码，保留新增表与已开户租户及业务数据，不通过删租户/删订单回退。新增白名单强制策略在回退前明确处理，不能静默卸载后让之前受限会员启动；生产迁移/回退不在本次本地授权范围。

## 12. 实施者可决定与完成门槛

类名、DTO、具体页面布局、测试脚本命名、索引命名和共享初始化代码位置由实施者在上述边界内确定；遇到需改变会员模型、真实外部账号交付、设备协议或公开部署的需求，应停下确认范围。

只有本地验收完成后才能称“配置化运营商接入已实现”；提交设计不意味着功能完成。设计需用户确认，随后生成实施计划，再进入代码开发与验证。
