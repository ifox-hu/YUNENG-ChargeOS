# 设备告警接入与处理：真实本地验证报告

日期：2026-11-04（Asia/Shanghai）。原始 JSON 使用 UTC ISO 时间，例如 `2026-11-03T17:46:51Z` 对应北京时间 11 月 4 日 01:46:51，并非日期记录错误。

## 结论与口径

本次新增设备告警持久接入、独立 RocketMQ 异步处理、事件幂等、活动工单合并、重试补偿、授权人工重放及运营查询；保留原用户报修路径。

**所有设备均为测试脚本生成的逻辑设备记录，非真实充电硬件，也不是同时维持 1000 条设备网络连接。所有性能数值是本地有限批次观测，不是生产流量、稳定最大容量或优化提升倍数。**

本地 HTTP 持久接收与后台处理是两个阶段。接收 P95 不能当作工单处理完成 P95；发送成功也不能当作业务处理成功。

## 环境

- Windows，Intel Core i7-13620H，16 个逻辑处理器，约 16 GB 内存。
- Docker Desktop Linux Engine 29.8.2，分配 16 逻辑 CPU、约 7.65 GiB 内存；MySQL 8.0.36、Redis、RocketMQ；operator 单实例，客户端 4.9.7。operator 未单设容器 CPU/内存限额，不代表宿主资源无限。
- Java 8 编译/运行，Spring Boot 2.7.18；前端使用项目现有 Vue 2 / Element UI，不是 Vue 3。
- 告警默认配置：4 消费线程、单批扫描 100 条、扫描间隔 1000ms、发送超时 3000ms、租约 30s、消费回执超时 120s、发送/消费失败上限各 12 次。
- 未进行专门的连接池/HTTP 线程容量调优；未另外采集其有效上限，不用本测试推断连接池收益。
- 各次运行的 CPU、内存、Docker 引擎资源、数据库版本及实际 operator 镜像记录在 `environment.json`。无专门预热、不做持续稳态负载，压测进程也运行在同一台电脑。

## 最终修复版本量化

### 集中告警：不同设备各报一次

| 场景 | HTTP 接收 | HTTP P95 | 数据库完成窗口/速率 | 接收至完成 P95 | 逐键对账 |
| --- | --- | --- | --- | --- | --- |
| 100 逻辑设备、300 唯一事件、32 请求并发 | 300/300；293.48 次/s | 236.13ms | 8.107s / 37.01 事件/s | 6.841s | 300 事件、300 告警、300 日志、100 活动工单，一一匹配 |
| 1000 逻辑设备、1000 唯一事件、64 请求并发 | 1000/1000；463.96 次/s | 218.13ms | 29.199s / 34.25 事件/s | 26.318s | 1000 事件、1000 告警、1000 日志、1000 活动工单，一一匹配 |

第二批 HTTP 测量窗口仅 **2.155s**。463.96 次/s 是该短批次的成功接收速率，**不能写成平台持续处理能力 464 QPS**。后台最终处理约 34.25 事件/s，端到端 P95 约 26.32s，不能省略后把接收延迟描述成告警已完成处理。

100 设备/300 事件场景验证“多个不同事件可以合并同设备同类活动工单”，并非把不同设备合为一张工单。

### 重复事件：HTTP 与 MQ 分开

- HTTP：同一逻辑设备、同一事件编号及载荷，32 请求并发、累计 1000 次接入，1000/1000 返回成功，仅保留 1 条持久事件、1 条告警、1 条日志、1 张工单。接收 P95 145.61ms，有限批次成功接收 356.55 次/s。
- MQ：对一个已经处理完成的事件，通过 Broker 中运行的 Java 探针**真实发送 1000 条 RocketMQ 消息**，确认目标消费者组相关队列的消费位点均越过探针末条，再核对仍为 1 事件/1 告警/1 日志/1 工单。
- MQ 测试不是只调 HTTP，也不是 mock 消费者；此轮是已完成事件的重复投递验证，不冒充 1000 条不同事件吞吐。探针执行时并行进行前端构建，因此其耗时不作为性能成果引用。

### 中断恢复

| 场景 | 停机期间接收 | 恢复观测窗口 | 最终结果 |
| --- | --- | --- | --- |
| Broker 停止后接收，再启动 Broker | 100/100，恢复前已持久化且 0 条完成 | 28.107s | 100 事件/100 告警/100 日志/100 工单，逐键对账通过 |
| Broker 停止后接收，重启 operator，再启动 Broker | 100/100，恢复前已持久化且 0 条完成 | 27.209s | 100 事件/100 告警/100 日志/100 工单，逐键对账通过 |

窗口从**执行启动 Broker 命令前**到**第一次轮询确认全量 PROCESSED**，包含启动、重连、重试等待和轮询误差，排除随后的对账；不是精确“Broker 已就绪到末条提交”耗时。重启 operator 场景的前置重启动作不在这 27.209s 内，事件接收至最终完成的数据库总窗口为 30.881s。两批均最终完成并成功清理，相关容器已恢复。

## 缺陷复现与修复证据

独立审阅后，三个问题先在真实 MySQL 测试中复现，再修复通过：

1. **设备转租与旧工单租户不同**：原逻辑可向旧租户活动工单写入新告警；现锁定后核对工单租户，不一致拒绝，事件/告警/日志无部分写入。
2. **1000 字合法描述溢出日志**：原日志拼前缀超过 VARCHAR(1000) 并回滚；现保留事件及首次工单原文，仅限制日志摘要长度。
3. **迟到消费失败污染人工重放**：原失败更新可让刚重放事件再次 DEAD；现重放代次递增，旧代次回写不影响新一轮。

对应 RED：`outputs/alarm-review-red.log`；GREEN：`outputs/alarm-review-green.log`。另发现快速重试被原客户端 1 秒防重复提交挡住，定向使用项目已有 `repeatSubmit:false` 约定绕过前置拦截，后台事件幂等继续生效。首次标志取值修复未通过的日志也保留，没有改写成通过记录。

## 局限与审阅取舍

- 仅模拟接入；不包含真实硬件、真实断网协议、跨节点集群、高可用切换或长期持续负载验证。
- UI 用真实管理员完成重放，后端以真实只读/创建角色验证拒绝访问；未另做只读角色“按钮隐藏”的浏览器断言，不将其计入已测项。
- 明确输入错误后仍需取消并重新新建，不提供就地修改按钮。响应不明时应先查原事件，避免换编号生成另一事件。
- 沿用 HTTP 200 + JSON `code` 的现有协议，成功率按业务 code 计算。
- 不在本次改造既有调度线程池，告警与积分调度可能互相影响；不承诺资源隔离或线上时延。
- 无基线的“提升几倍”、极限 QPS、生产设备规模、零重复发送、无限自动恢复均不能从本测试推出。

## 可用于简历的表述

开发设备告警接入与处理模块，采用事件持久化、RocketMQ 异步处理及租约补偿，按设备与故障类型合并活动工单；本地构造 **1000 台逻辑设备、64 并发提交 1000 条告警**，全部处理并完成逐事件对账；**1000 条真实 MQ 重复投递**仅保留一份工单关联与处理日志，支持失败监控及授权重放。
